# Task 29: 抽出パイプラインの堅牢化（1バッチの破損で全体が止まる問題）

## 背景

Task 27/28 の抽出スクリプトを楽天 1,000 件に対して実行したところ、**400 件目で停止**し、
成果物が空のまま終了した（`python exit=1`）。

```
WARNING: Batch attempt 1/2 failed: Expecting ',' delimiter: line 119 column 50 (char 3309)
WARNING: Batch attempt 2/2 failed: Expecting ',' delimiter: line 119 column 50 (char 3309)
ERROR: batch extraction failed after retries
```

### 根本原因（生応答を捕まえて特定済み）

モデルは `source_title` を**そのまま複製して返す**設計になっている。
問題のタイトルはこれ:

```
入力（生データ）: 【ウイスキー】イチローズモルト　モルト＆グレーン　“クラシカルエディション”　700ml　2本セット
                                                              ^U+201C            ^U+201D
モデルの出力    : ..."source_title": "【ウイスキー】...　"クラシカルエディション"　700ml..."
                                                        ^半角 " に正規化されて JSON が壊れる
```

**入力は全角の `“ ”` だが、モデルが半角 `"` に正規化して返すため JSON が壊れる。**
入力側のサニタイズでは防げない（モデル自身が壊している）。

### 設計上の欠陥（3 つ）

1. **モデルに `source_title` を複製させている。** スクリプトは入力タイトルを持っているのだから、
   モデルに返させる必要がない。複製させる限り、この種の破損は再発する
2. **1 バッチの破損で全体が止まる。** 残り 600 件の処理が失われる
3. **リトライが決定論的に同じ失敗を繰り返す。** 同一入力・同一温度なので 2 回とも同じ位置で失敗する

`/home/ttakahashi/workspace/whiskey`（ブランチ `fix/brand-detection-canonical-name`）

## スコープ

`scripts/extract_whiskey_names_claude_sonnet.py` と `tests/` のみ。
`lambda/` `infra/` `frontend/` およびカタログ JSON は触らないこと。

## 実装内容

### 1. `source_title` をモデルに返させない（本質的な修正）

- モデルの出力スキーマから **`source_title` を削除**する
- モデルには **`input_index`（バッチ内の 0 始まりの位置）だけ**を返させる
  （現状すでに `input_index` を返しているので、それを正とする）
- `source_title` は**スクリプト側が入力配列から再付与**する
- `MODEL_RESULT_FIELDS` から `source_title` を外し、検証もそれに合わせる

これによりタイトル内の引用符・バックスラッシュ・制御文字に起因する JSON 破損が構造的に消える。
トークン消費も減る。

**注意:** 既存の `_observed_in_title` 等は `source_title` を使って
「モデルが発明した値でないか」を検証している。再付与後の `source_title` を使えば
同じ検証がそのまま成立する。この検証は**維持すること**。

`input_index` が欠落・重複・範囲外の場合はそのレコードを破棄し、警告を出すこと
（推測で対応付けない）。

### 2. 1 バッチの失敗で全体を止めない

- バッチの解析に失敗しても**残りのバッチの処理を続行**する
- 失敗したバッチは記録し、最後にサマリで「失敗バッチ数・対象インデックス範囲」を報告する
- 全バッチ終了後、**成功分の成果物は必ず書き出す**（現状は空ファイルになる）
- 失敗が 1 件でもあれば終了コードは非ゼロにするが、**成果物は残す**

### 3. リトライを決定論的な繰り返しにしない

同一入力で 2 回叩いても同じ結果になる。段階的に条件を変えること:

1. 1 回目: 通常どおり
2. 2 回目: **バッチを半分に分割して再試行**（20 件 → 10 件 × 2）。
   トークン長やモデルの出力揺れに起因する破損はこれで抜けられることが多い
3. 3 回目: **1 件ずつ**処理する。1 件が壊れていても他の 19 件は救われる
4. それでも失敗した個別項目のみ破棄し、記録する

### 4. 失敗時に生応答を保存する

解析に失敗したときは、モデルの生応答を
`scripts/catalog/failed_batches/<timestamp>_<index>.txt` に保存する
（`.gitignore` に追加すること。楽天由来データなので public リポジトリにコミットしない）。

ログには**先頭 200 文字と失敗位置の前後 100 文字**を出す。
今回、生応答が残っていなかったため原因特定に余計な手間がかかった。

### 5. JSON 抽出の堅牢化

モデルは ```` ```json ```` フェンスで囲んで返すことがある。
現状の処理を確認し、フェンスの有無・前後の余分なテキストに耐えるようにすること。

## テスト（Bedrock を呼ばないこと。応答はスタブ）

1. **引用符を含むタイトルの回帰**:
   入力タイトルに `“クラシカルエディション”` を含み、モデルが `source_title` を返さない
   応答を与えたとき、`source_title` がスクリプト側で正しく再付与される
2. `input_index` が欠落したレコードが破棄され、警告が出る
3. `input_index` が重複・範囲外のレコードが破棄される
4. **1 バッチが壊れても残りのバッチが処理され、成果物が書き出される**
   （現状は空ファイルになる。ここが最重要）
5. 失敗バッチがサマリに記録され、終了コードが非ゼロになる
6. リトライでバッチが分割される（20 → 10 × 2 → 1 件ずつ）
7. 1 件だけ壊れているバッチで、残り 19 件が救われる
8. 生応答が `failed_batches/` に保存される
9. `_observed_in_title` 系の検証が再付与後の `source_title` で従来どおり働く
   （モデルが発明した値を弾く挙動を壊さない）
