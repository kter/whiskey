# Task 27: 評価用取り込みを実際のクライアント経路に合わせる

## 背景（実写真27枚で再現済み）

タスク26 で作った `scripts/eval/import_real_photos.py` を 621 の実写真27枚に対して実行したところ、
**1枚目の途中で全体が異常終了した**。

```
ERROR: unable to normalize image: .../IMG_0418.HEIC
ImageNormalizationError: Image exceeds the 20 MP or 8000 px dimension limit
（実測 4284x5712 = 24.5 MP）
```

`normalize_image` の判定自体は正しい。問題は**評価入力の作り方**にある。

本番の経路はこうなっている:

1. ブラウザが `frontend/utils/imageResize.ts` で縮小する。
   HEIC はまず `heic-to` で JPEG(q0.92) 化し、そのうえで
   `{maxDimension, quality}` の段階列 — `1600/0.85 → 1600/0.7 → 1600/0.55 →
   1280/0.7 → 1280/0.55 → 1024/0.55` — を上から試し、
   **3,670,016 バイト以下**に収まった最初の結果を使う。
2. その**縮小済みバイト列**が S3 に上がり、analyze がそれを受け取る。
3. analyze 側で `normalize_image` の上限（20MP / 8000px / 3.5MB）が効く。

つまり 24.5MP の原寸が analyze に届くことは実運用では起こらない。
現在の取り込みは 1 を飛ばして原寸を 3 に通しているため、
**本番では正常に扱える写真を評価セットから落としてしまう**。評価対象が実物とずれる。

## スコープ

`scripts/eval/import_real_photos.py` と `tests/eval/test_import_real_photos.py`、
および `.gitignore` の 1 行。**`lambda/` `infra/` `frontend/` は変更しない。**
`whiskey_common.images.normalize_image` の実装も変更しない（本番の契約であり、
評価の都合で緩めてはならない）。

## 変更1: クライアント側の縮小を再現してから正規化する

取り込みは「ブラウザがやること」を先に行い、その結果を `normalize_image` に渡す。

- 新しい内部関数として、`frontend/utils/imageResize.ts` と**同じ段階列**を定数で定義する
  （`(1600, 0.85), (1600, 0.7), (1600, 0.55), (1280, 0.7), (1280, 0.55), (1024, 0.55)`）。
  **フロントの値をコメントで参照し、乖離したら気付けるようにすること。**
- 各段階で「長辺を `maxDimension` 以下に縮小 → JPEG(quality) で書き出し」を行い、
  **3,670,016 バイト以下**になった最初の結果を採用する。
- 縮小前に `ImageOps.exif_transpose` を適用すること（HEIC/JPEG の回転情報は
  縮小前に解決しないと向きが狂う。本番のブラウザ経路も canvas 描画時に解決している）。
- どの段階でも収まらなければ、そのファイルは**取り込み失敗**として扱う（後述の変更2）。
- 縮小後のバイト列を **これまでどおり `normalize_image` に通す**。ここは残すこと —
  analyze が最終的に適用する関門を評価入力も通っていることの保証になる。
- 出力ファイル名は従来どおり **最終バイト列の sha256 先頭16文字**。縮小段階が決定的なので
  冪等性は保たれる。

**デコード爆弾への配慮**: 縮小のためにデコードする時点で巨大画像を展開することになる。
`Image.MAX_IMAGE_PIXELS` を明示的に設定し（例: 80MP）、超過は取り込み失敗にすること。
ここはローカルの開発者ツールであり信頼できない入力を扱う前提ではないが、無防備にはしない。

## 変更2: 1枚の失敗で全体を落とさない

27枚のうち1枚が失敗しただけで全部やり直しになるのは道具として使いにくい。

- 各ファイルの失敗を捕捉して**続行**する。
- レポートに `failures` 配列を追加する。各要素は
  `{"reason": "<短い理由>", "source_format": "<形式>"}` のみとし、
  **入力ファイルのパスや名前は絶対に含めない**（レポートは stdout に出て
  コピペされうる。ファイル名は撮影日や場所を含みうる）。
  どのファイルかを 621 が特定できるよう、パスは **stderr** にだけ出す。
- 1件でも失敗したら終了コードは **1**。ただし成功分の書き出しとレポート出力は行う。
- `imported_files` は成功数、`failed_files` を新設する。

## 変更3: `manifest.example.json` が git に入っていない

`.gitignore` の 145 行目に包括的な `*.json` があるため、
**`scripts/eval/manifest.example.json` は一度もコミットされていない**
（`git check-ignore -v` で確認済み。タスク26 で `manifest.schema.json` は
`!` で救済されたが、example は取り残されている）。

同ファイルへの `!scripts/eval/manifest.example.json` を、既存の救済行の並びに追加する。
`.gitignore` の 147 行目付近にある「これらが ignore されるとカタログがローカルにしか
存在せず、CI と他のクローンが壊れる」というコメントと同じ理由である。

**受入条件**: `git check-ignore scripts/eval/manifest.example.json` が何も報告しないこと、
かつ `git status` に同ファイルが未追跡として現れること。

## テスト（`tests/eval/test_import_real_photos.py` に追加）

- **20MP を超える画像（例: 4284x5712 相当を合成）が取り込めること**。
  出力が 1600px 以下・3.5MB 以下・JPEG・メタデータ無しであること。
  これが本タスクの回帰テストの本体。
- 段階列が上から順に試され、**3.5MB に収まった最初の段階が採用される**こと
  （収まらない段階をスタブ等で作り、採用された寸法・品質を検証する）。
- `Image.MAX_IMAGE_PIXELS` を超える入力が**失敗として扱われる**こと。
- **1枚失敗しても他が取り込まれ、終了コードが 1 になる**こと。
- **失敗レポートに入力パス・ファイル名が含まれない**こと（プライバシー回帰防止）。
- 既存のテスト（EXIF 除去・sha256 命名・冪等・対象外ファイル無視）が緑のままであること。

## 実装メモ

- 621 の実写真は HEIC 27枚で、少なくとも1枚が 4284x5712。**パスをハードコードしないこと。**
- 縮小の品質は本番と厳密一致しない（Pillow と canvas は別実装）。
  **厳密一致は求めない** — 求めるのは「寸法とバイト数の上限が同じ経路を通ること」。
  この限界を docstring に1行書いておくこと。
